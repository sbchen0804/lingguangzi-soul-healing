# 靈魂療癒章節網站 Skill 設計規格

日期：2026-09-01

狀態：待使用者最終審閱

適用專案：`lingguangzi-soul-healing`

## 1. 目的

將已完成的第 521 章網站製作經驗，整理為可重複執行的 Codex Skill 與標準作業流程。使用者只需建立章節目錄、放入來源檔案並填寫 `chapter.json`，Skill 即可完成檢查、內容轉換、章節頁面產生、本機預覽與發布前驗收。

每章的網站內容在使用者明確確認前不得提交或發布至 GitHub。設計規格與實作計畫等專案文件可獨立提交。Skill 的預設終點是「本機預覽完成、檢查報告完成、等待確認」。

## 2. 核心內容與讀者定位

網站以一般大眾為主要讀者，整合三個解讀面向：

- 專業醫者：健康、身體、心理與生理醫學。
- 人生智者：正念、當下、生命經驗與超然智慧。
- 屬靈陪伴：信、望、愛與交托，但首頁與主要敘事不刻意強調宗教標籤。

原作者為柯萬盛醫師，筆名靈光子。系列內容已取得作者同意公開分享；每章頁尾須保留作者署名及授權说明。

## 3. 已選定方案

採用「Skill＋`chapter.json`＋共用模板＋確定性轉換腳本」方案。

不採純人工 SOP，因其仍需反覆複製、調整及檢查；現階段也不建立 CMS 後台，避免增加帳號、資料庫、資安與維護負擔。此方案可保留人工審美判斷，同時將檔案檢查、PDF 轉頁、文字擷取、頁面組裝與 QA 自動化。

## 4. 網站資訊架構

網站維持單一 GitHub 儲存庫與單一公開網站：

```text
soul-healing-site/
├─ index.html                  # 系列總目錄
├─ site.config.json            # 全站設定、公開網址與分析服務
├─ shared/                     # 共用 CSS、JavaScript 與介面資源
├─ chapters/
│  ├─ 520/
│  │  ├─ index.html
│  │  └─ assets/
│  ├─ 521/
│  │  ├─ index.html
│  │  └─ assets/
│  └─ ...
└─ legacy/                     # 舊第 521 章網址相容處理（如需要）
```

每章具有獨立、可分享的 canonical URL，例如：

```text
https://sbchen0804.github.io/lingguangzi-soul-healing/chapters/520/
```

系列首頁列出已發布章節。現有第 521 章公開網址必须保持可访问，并导向或兼容新的章節结构。

## 5. Skill 結構

Skill 建議命名為 `lingguangzi-chapter-site`：

```text
lingguangzi-chapter-site/
├─ SKILL.md
├─ agents/
│  └─ openai.yaml
├─ references/
│  ├─ chapter-schema.md
│  ├─ content-and-visual-rules.md
│  └─ qa-and-release.md
├─ scripts/
│  ├─ validate-chapter.*
│  ├─ extract-lyrics.*
│  ├─ render-pdf-pages.*
│  └─ build-chapter.*
└─ assets/
   └─ chapter-template/
```

`SKILL.md` 僅保留觸發條件、工作流程、授權邊界與參考文件路由。詳細 schema、視覺規則及 QA 置於 `references/`；重複且需要一致結果的轉換工作由 `scripts/` 完成。

## 6. 章節輸入目錄

標準目錄如下：

```text
靈魂療癒系列第 520 章/
├─ chapter.json
├─ 原圖文/
│  ├─ 封面圖片
│  └─ 原作 PDF
├─ 詩歌創作/
│  ├─ 歌曲 MP3 或 M4A
│  └─ 歌詞 DOCX、PDF 或 TXT
└─ 精煉篇_找回生命的靈魂處方/
   ├─ 生命智慧圖卡
   ├─ 精煉篇 PDF
   ├─ Podcast MP3 或 M4A
   └─ 影片 MP4（選用，可有多個）
```

檔名不必每章完全一致；`chapter.json` 是檔案角色與顯示順序的唯一依據。

## 7. `chapter.json` 資料契約

代表性格式：

```json
{

  "chapter": 520,
  "title": "讓風穿過心的門",
  "subtitle": "本章副標題",
  "theme": {
    "keywords": ["健康", "靈性", "安穩", "平靜"],
    "visual_notes": "可選填的本章意象"
  },
  "original": {
    "cover": "原圖文/讓風穿過心的門.png",
    "pdf": "原圖文/靈魂療癒系列第520章.pdf"
  },
  "song": {
    "title": "讓風穿過心的門",
    "audio": "詩歌創作/讓風穿過心的門.mp3",
    "lyrics_source": "詩歌創作/讓風穿過心的門.pdf"
  },
  "refined": {
    "title": "找回生命的靈魂處方",
    "items": [
      {
        "type": "image",
        "role": "wisdom-card",
        "title": "生命智慧圖卡",
        "file": "精煉篇_找回生命的靈魂處方/520_摘要.png",
        "order": 1
      },
      {
        "type": "document",
        "role": "full-text",
        "title": "精煉篇全文",
        "file": "精煉篇_找回生命的靈魂處方/520_簡報.pdf",
        "display": "online-pages",
        "order": 2
      },
      {
        "type": "audio",
        "role": "podcast",
        "title": "Podcast",
        "file": "精煉篇_找回生命的靈魂處方/520_PODCAST.m4a",
        "order": 3
      },
      {
        "type": "video",
        "role": "feature-video",

        "order": 4

    ]
  },
  "sharing": {
    "description": "可選填；未填時由標題、副標題與主題產生精準摘要",

```

`refined.items` 為可擴充陣列。未提供的選用項目直接省略；多張圖卡、多段音訊或多支影片可分別增加項目。`order` 不得重複。

## 8. 內容正規化

### 8.1 原圖文

- 原作者封面圖片不得改圖、裁字或重新生成。
- 原作 PDF 轉成逐頁圖片，直接置於網頁內閱讀。
- 保留下載 PDF 的次要連結，但主要動線是線上閱讀。
- 轉頁後核對頁數、順序、寬高比與可讀性。

### 8.2 歌詞

- DOCX、文字型 PDF 或 TXT 均轉為語意化 HTML。
- 掃描型 PDF 才使用 OCR。
- 保留原始歌詞文字、段落、主歌、副歌與橋段標示，不得自行重寫。
- OCR 或格式擷取有疑義時，在最終檢查報告集中列出，不逐項打斷使用者。

### 8.3 精煉篇

- 圖卡直接在頁面顯示，不另開沒有返回入口的圖片頁。
- PDF 或簡報 PDF 轉為逐頁圖片，依序垂直排列。
- 音訊與影片使用瀏覽器原生控制項，置於各自獨立內容區塊。
- 內容區塊依 `order` 正常文件流排列，不使用可能覆蓋後續內容的固定高度或絕對定位。

## 9. 主視覺系統

每章依標題、文章內容與生命主題重新設計主視覺，不只是更換章號。

共同風格：

- 水彩彩繪。
- 健康、靈性、安穩、平靜。
- 面向一般大眾，不以強烈宗教符號作為第一印象。
- 色彩、留白與光線維持同一系列語言，但畫面意象依章節變化。

產生兩個視覺資產：

- `hero-{chapter}.jpg`：網站主視覺，不把章名烙入圖片；系列名稱、章號、標題與副標題以 HTML 疊加。
- `share-{chapter}.jpg`：1200×630 社群分享圖，沿用同一水彩畫面，可加入系列名稱、章號與精簡主題，以確保 LINE、Facebook 等預覽能直接傳達內容。

主視覺需在手機與電腦採 `object-fit: cover` 或等效響應式方式裁切，不得拉伸變形。

## 10. 第 521 章字體基準

後續章節沿用第 521 章已確認的手機閱讀字級，不得為容納文字任意縮小：

| 元素 | 手機版基準 |
| --- | --- |
| 系列名稱 | `1.3rem` |
| 主標題 | `clamp(1.55rem, 7vw, 2.05rem)` |
| 主旨句 | `1.05rem` |
| 閱讀方式提示 | `1rem` |
| 圓圈主標題 | `1.06rem` |
| 圓圈說明 | `0.8rem` |
| 正文 | `1.04rem` |
| 閱讀歌詞入口 | `1.06rem` |
| 作者署名與公開說明 | `1.02rem` |

三個圓圈說明原則上不斷行。若文案過長，優先精簡文案，不以縮小字體處理。正文維持舒適行距與段落間距。

## 11. 頁面導覽與首次進入行為

首次以章節 canonical URL 進入時，頁面必須位於最頂端，完整呈現系列名稱、主視覺、章號、標題與副標題。

三個圓圈分別導向原圖文、詩歌呈現與精煉篇。選取後，所選圓圈改為系列綠色並精準定位到段落。

右側 Go Top 的產品定義是「回到三個閱讀方式選項」，不是瀏覽器網址錨點：

- 點擊時捲動到選項區。
- 不把 `#entry-{chapter}` 寫入網址。
- 舊的 `#entry-{chapter}` 網址首次進入時，清除該錨點並回到頁面頂端。
- `#original-{chapter}`、`#song-{chapter}`、`#refined-{chapter}` 等有分享價值的深層連結保留。

目前第 521 章 Go Top 使用 `href="#entry-521"`，會讓錨點留在網址並在下次進入時直接跳過主視覺。迁移共用模板时须修正，并增加回归测试。

## 12. 媒體體驗

- 不自動播放音訊或影片。
- 同一時間只允許一個音訊或影片播放。
- 切換站內段落時，正在播放的音訊可持續，並提供固定暫停、繼續與停止控制。
- 離開、關閉或隱藏頁面時停止所有媒體，避免使用者失去控制。
- 播放器在手機與電腦不得超出內容寬度，也不得遮蔽 Go Top 或正文。
- 影片採響應式 16:9 容器或依來源比例呈現，不得變形。

## 13. 響應式設計與驗收矩陣

發布前必須同時完成自動檢查與實際視覺檢查。

測試寬度：

- 手機直式：320、375、390、430px。
- 手機橫式：代表性橫向尺寸。
- 平板：768、1024px。
- 電腦：1280、1440、1920px。
- 瀏覽器文字或頁面放大至 200%。

每個尺寸至少檢查：

- canonical URL 冷啟動時 `scrollY = 0`，主視覺與主題可見。
- 手機首屏能在不破壞主視覺的前提下看見三個圓圈入口。
- 圓圈不變形；文字不溢出、不互相覆蓋。
- 頁面沒有非預期橫向捲動。
- 主視覺不拉伸，重要意象未被不當裁掉。
- 點選三個入口後定位正確，選中狀態正確。
- Go Top 回到選項區且不污染網址；重新整理仍從預期位置開始。
- 原圖文與精煉篇每一頁完整顯示，不空白、不重疊。
- 音訊、影片、圖卡及歌詞不超出頁面。
- 浮動控制項不遮蔽正文、頁碼或彼此重疊。
- 長標題、作者署名與授權說明不被截斷。

第 521 章作为视觉及交互回归基准；自动截图与其设计变量比较，但每章主视觉内容可以不同。

## 14. 計數器與隱私

採用 GoatCounter 作為 GitHub Pages 的輕量統計服務：

- `site.config.json` 保存公開站台代碼與服務端點，不保存密碼或 API 金鑰。
- 正式網站計數；localhost、127.0.0.1 與預覽環境不計數。
- 每章頁尾可顯示「本章瀏覽次數」。
- 系列首頁可顯示全站累計瀏覽次數。
- 管理後台查看全站、各章與來源統計。
- 對外用語為「瀏覽次數」，不宣稱絕對獨立人數。
- 計數器載入失敗時顯示非阻塞的替代狀態，不影響閱讀。
- 頁尾加入簡短、清楚的統計與隱私說明。

第一次正式啟用前需要使用者完成一次 GoatCounter 帳號及站台代碼設定；後續章節由 Skill 自動沿用。若正式發布時尚未設定，網站可本機預覽，但發布檢查須將 Counter 標記為未完成。

## 15. Meta、社群分享與結構化資料

每章自動產生：

- `<title>` 與 `meta name="description"`。
- canonical URL。
- Open Graph：`og:type`、`og:locale`、`og:site_name`、`og:title`、`og:description`、`og:url`、`og:image`、尺寸與替代文字。
- Twitter/X large image card 對應欄位。
- `Article` JSON-LD，包含章名、摘要、作者、圖片、網址、發布及更新日期。

Meta 摘要預設由章名、副標題與主題產生；`chapter.json` 的 `sharing` 可覆寫。分享圖片必須使用公開絕對 HTTPS URL，发布后检查可读取性、1200×630 比例、合理档案大小及文字准确度。

## 16. 建置資料流

1. 讀取使用者指定章節目錄與 `chapter.json`。
2. 驗證 schema、章號、必需檔案、檔案類型、路徑與 `order`。
3. 複製原封面，不變更內容。
4. 將 PDF 轉為逐頁圖片並核對頁數。
5. 將歌詞 DOCX、PDF 或 TXT 正規化為 HTML；必要時執行 OCR。
6. 依本章內容產生水彩主視覺與分享圖。
7. 由共用模板產生 `/chapters/{chapter}/`。
8. 更新系列總目錄，但不發布。
9. 執行內容、響應式、導覽、媒體、Meta 與 Counter 測試。
10. 產生本機預覽與一份集中檢查報告。
11. 等待使用者明確確認發布。
12. 確認後才 commit、push，並驗證 GitHub Pages 公開網址。

## 17. 錯誤處理與集中回報

阻斷建置或發布的錯誤：

- `chapter.json` 無法解析、章號不一致或必需欄位缺失。
- 指定檔案不存在、格式不支援或同一 `order` 重複。
- PDF 轉頁失敗、頁數不符或產生空白頁。
- 歌詞無法擷取且 OCR 仍不足以可靠辨識。
- 音訊或影片無法載入。
- 響應式測試出現溢出、重疊或錯誤定位。
- canonical、Open Graph 圖像或正式站台連結錯誤。

非阻斷警告：

- OCR 低信心文字，需要使用者在預覽中核對。
- 選用的影片、Podcast 或圖卡未提供。
- 標題或說明過長，Skill 已提出精簡建議。
- 本機階段無法實際驗證正式 Counter 數字。

所有問題在同一份報告集中呈現，避免反覆逐項詢問。阻斷錯誤必須修正後才可進入發布確認。

## 18. 發布權限與版本控制

以下語句才視為發布授權：

```text
確認發布第 N 章
```

「建立」、「預覽」、「看起來可以」或 `chapter.json` 中的任何欄位都不構成 GitHub 發布授權。

發布流程：

1. 確認工作樹變更範圍只包含本章、共用模板必要更新及總目錄。
2. 執行完整測試與 production build。
3. 建立清楚的 Git commit。
4. Push 至 GitHub。
5. 等待 GitHub Pages 部署完成。
6. 驗證章節 canonical URL、資產、Meta、分享圖、媒體及 Counter。
7. 回報 commit、公開網址與驗證結果。

Skill 不建立 GitHub Release 資產包，除非使用者另行要求；本規格中的「發布」主要指 GitHub Pages 上線。

## 19. 第 521 章遷移與相容性

Skill 與共用模板建立後，第 521 章需納入同一架構並完成一次回歸驗證：

- 保留現有內容與已確認字體。
- 修正 `#entry-521` 造成首次進入跳過主視覺的問題。
- 確保舊公開根網址仍可使用。
- 不改寫原作、歌詞或精煉篇內容。
- 重新驗證 PDF、音訊、Go Top、手機定位及頁尾署名。

## 20. 完成標準

Skill 只有在下列條件全部成立時才算完成：

- 新章可由有效的 `chapter.json` 與標準輸入目錄建置。
- DOCX、PDF、TXT 歌詞可轉為網頁文字。
- PDF 可轉為無重疊的線上逐頁閱讀。
- 圖片、音訊、Podcast 與選用影片可依清單順序呈現。
- 每章有一致但不制式的水彩主視覺。
- 第 521 章字級、首次進入、Go Top 與響應式規則均成為自動驗收條件。
- 手機、平板與電腦測試全部通過。
- Meta、分享圖與 Counter 設定可驗證。
- 本機預覽完成後停止，除非取得當次明確發布授權。
- 第 520 章可作為第一個新章節完整演練，使用者不必再次說明既有規則。
